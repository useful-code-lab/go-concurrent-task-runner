# Go Concurrent Task Runner

Практический пример **конкурентного планировщика и исполнителя задач на Go**, который показывает, как построить надёжную систему обработки задач с контролем количества воркеров, отменой и таймаутами, обработкой паник, сбором метрик и профилированием производительности.

Проект полезен разработчикам, которые хотят не просто изучить синтаксис Go, а разобраться, **как проектировать и оптимизировать конкурентные системы на практике**.

---

## 🎯 Что вы получите, изучив проект

Этот репозиторий можно использовать как практический пример для изучения архитектуры систем обработки задач.

После изучения кода вы сможете лучше понимать, как:

* организовать выполнение большого количества задач через **Worker Pool**;
* ограничивать количество одновременно работающих горутин;
* передавать задачи между компонентами через **channels**;
* управлять отменой и таймаутами через `context.Context`;
* корректно завершать приложение и воркеры через **Graceful Shutdown**;
* изолировать ошибки отдельных задач и предотвращать падение всего процесса;
* безопасно собирать метрики из нескольких горутин;
* уменьшать количество аллокаций с помощью `sync.Pool`;
* находить узкие места приложения с помощью `pprof`;
* проверять конкурентный код с помощью **Race Detector**;
* измерять пропускную способность системы с помощью benchmark-тестов.

Таким образом, репозиторий можно использовать как **учебный шаблон для создания собственных конкурентных сервисов и фоновых обработчиков на Go**.

## 🧩 Что реализовано

### Worker Pool

Задачи поступают в очередь и распределяются между несколькими воркерами.

Это позволяет контролировать конкурентность и не создавать неограниченное количество горутин при увеличении нагрузки.

```text
             ┌─────────────┐
             │    Tasks    │
             └──────┬──────┘
                    │
                    ▼
             ┌─────────────┐
             │ Task Queue  │
             └──────┬──────┘
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
      Worker 1  Worker 2  Worker 3
          │         │         │
          └─────────┼─────────┘
                    ▼
             Result / Metrics
```

Такой подход используется как основа для различных систем фоновой обработки:

* обработки очередей;
* фоновых задач;
* batch-операций;
* параллельных вычислений;
* обработки большого количества независимых операций.

## ⚡ Конкурентность в Go

Проект показывает практическое применение:

* goroutines;
* buffered и unbuffered channels;
* `select`;
* `sync`;
* `atomic`;
* `context`.

Вместо отдельных изолированных примеров все эти механизмы используются вместе внутри одной работающей системы.

Это позволяет увидеть, **как отдельные возможности Go взаимодействуют друг с другом в реальном конкурентном коде**.

---

## ⏱ Отмена и таймауты

Каждая задача может выполняться с использованием `context.Context`.

Это позволяет:

* устанавливать ограничения по времени;
* отменять выполнение;
* корректно завершать длительные операции;
* передавать сигнал отмены между компонентами.

Например, задача, которая превысила допустимое время выполнения, может быть остановлена без необходимости завершать весь процесс.

---

## 🛡 Защита от паник

Ошибка внутри одной задачи не должна приводить к остановке всего worker pool.

Поэтому выполнение задач защищено механизмом `recover`.

В результате отдельная неисправная задача может завершиться ошибкой, а остальные воркеры продолжают обработку очереди.

Это демонстрирует один из практических подходов к повышению устойчивости фоновых обработчиков.

## 📊 Метрики выполнения

Проект собирает информацию о работе планировщика:

* количестве выполненных задач;
* количестве паник;
* времени выполнения;
* результате обработки.

Для безопасного обновления счётчиков из нескольких горутин используется `atomic`.

Это позволяет наблюдать за поведением системы во время выполнения и использовать полученные данные для дальнейшего анализа.

## 🧠 Оптимизация памяти

Для уменьшения количества временных объектов используется `sync.Pool`.

Это позволяет переиспользовать объекты вместо постоянного создания новых.

На практике такой подход может помочь:

* сократить количество аллокаций;
* уменьшить нагрузку на Garbage Collector;
* снизить накладные расходы при интенсивной обработке задач.

При этом проект позволяет на практике исследовать, **когда оптимизация памяти действительно имеет смысл, а когда она усложняет код без существенной пользы**.

## 🧪 Тестирование и Benchmark

Проект содержит unit-тесты и benchmark-тесты.

Запуск benchmark:

```bash
go test ./internal/runner/ -bench=.
```

Benchmark позволяет измерять производительность runner и сравнивать результаты после изменения реализации.

Для проверки конкурентного кода можно использовать:

```bash
go test -race ./...
```

Race Detector помогает обнаруживать состояния гонки, которые могут возникать при одновременном доступе нескольких горутин к общим данным.

---

## 🛑 Graceful Shutdown

Планировщик умеет корректно завершать работу приложения.

Обрабатываются системные сигналы, после чего система:

1. прекращает принимать новые задачи;
2. передаёт сигнал завершения воркерам;
3. корректно завершает активные операции;
4. освобождает используемые ресурсы.

Это показывает, как организовать жизненный цикл конкурентного сервиса, а не только его запуск.

## 🏗 Архитектурные принципы

В проекте используются несколько важных принципов разработки:

### Interface-driven design

Работа с задачами построена через интерфейсы.

Это позволяет отделить механизм выполнения задач от конкретной бизнес-логики и добавлять новые реализации без изменения основного runner.

### Разделение ответственности

Основные компоненты отвечают за разные задачи:

* постановку задач;
* выполнение;
* управление воркерами;
* обработку жизненного цикла;
* сбор метрик;
* профилирование.

Такую структуру проще тестировать, расширять и исследовать.
